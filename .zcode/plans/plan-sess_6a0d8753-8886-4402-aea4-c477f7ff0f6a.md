## 总体设计

新增「应用层意图路由 + SSE 对话 API + React 聊天前端」，同时按高星 Agent 提示词模式重写主/子 Agent 提示词并同步工具说明。

```
用户消息 → 意图分类 Agent(结构化输出: CHAT/TOOL_CALL/PLANNING/RAG)
  ├─ CHAT      → 主 Agent（注入"禁止委派"路由指令，直接回答）
  ├─ TOOL_CALL → 主 Agent（注入"禁止委派"路由指令，调工具后回答）
  ├─ RAG       → 预留分支：RagService 当前返回不可用 → 回退主 Agent 直接回答（后续接知识库零改造）
  └─ PLANNING  → 主 Agent 正常运行（提示词引导其委派 planning-agent）
```

## 1. Skills 同步（需求 1）

- weather/hotel/attraction 三个 skill 已与 Java 工具类一致（已核实）；train/flight 两个已是 MCP 工具版本
- 主要工作：**删除主/子 Agent 提示词里硬编码的过期工具清单**（仍写着已删除的高德 `searchTrainTickets` 等），改为简短能力概览 + 指向 skills 技能文件，工具细节以 skills 为唯一事实源

## 2. 提示词优化（需求 2）

参考 Claude Code / OpenHands / MetaGPT / LangGraph supervisor / Qwen-Agent 旅行规划提示词的成熟结构重写：

**TravelMasterAgent.SYS_PROMPT**：一句角色定义 → IMPORTANT 硬约束（数据必须来自工具、不编造票价车次）→ 意图路由规则（"For X use Y" 条件映射 + **"何时不得委派规划 Agent"反向清单**）→ 任务拆分与 task_backlog 规范（保留现有 MD 文件协作机制）→ 工具使用政策（独立信息并行调用、失败不重复重试、名称与工具返回精确一致）→ 输出语气与格式

**ItineraryAgent.SYS_PROMPT**：worker 身份锚定（"你只执行主 Agent 分派的任务"）→ Scope（只做被要求的事，越界发现转为 follow-up 建议）→ 协作文件读写协议（三个 MD 文件的读写时机与格式）→ 可用工具指向 skills（MCP 工具名 `mcp__c12306__*` / `mcp__variflight__*`）→ 异常协议（工具失败上报原因、歧义选最可能解释并注明假设、同一失败最多重试 1 次）→ 汇报格式（做了什么 + 一句话结论，好/坏示例对照）+ 行程草案输出结构（每日时间线连续衔接、费用汇总、注意事项）

## 3. 意图识别（需求 3，代码层先分类）

新增：
- `agent/IntentType.java`（枚举 CHAT/TOOL_CALL/PLANNING/RAG）+ `dto/IntentResult.java`（{intent, reason}）
- `agent/IntentClassifier.java`：轻量 ReActAgent（qwen-plus、无工具无子代理），`call(msg, IntentResult.class)` 结构化输出分类；分类提示词用 few-shot 条件映射写法。按官方 Web 模式**每次分类新建实例**（ReActAgent 非线程安全，Model 可共享）
- `config/AgentConfig.java`：注册 `IntentRouterMiddleware`（onSystemPrompt 阶段，按 RuntimeContext 中的 intent 属性给主 Agent 追加本轮路由指令：非 PLANNING 意图追加"本轮禁止委派规划子 Agent"；若 Middleware API 与 2.0.3 实际签名不符，回退方案为仅对 PLANNING 以外意图在发送消息时附带一次性指令）
- `service/RagService.java`：预留接口 + 桩实现（`isAvailable()`=false、`retrieve()`=空列表，代码路径完整，后续接 SimpleKnowledge+PgVectorStore 零改造）

## 4. 后端对话 API（需求 4 支撑）

- `entity/` + `repository/`：Conversation、Message 两个 JPA 实体（messages 的 JSONB 列暂不映射，仅用 role/content/conversation_id/user_id/created_at），user_id 固定匿名 "guest" 用户（服务启动时 getOrCreate）
- `service/ConversationService.java`：会话 CRUD（首条消息自动生成标题）、消息持久化（用户消息入库 → 路由 → 助手回复在 AgentEndEvent 时入库）
- `service/ChatService.java`：核心编排（分类 → 路由 → 订阅 `agent.streamEvents(msg, ctx)`，`subscribeOn(boundedElastic)`）
- `controller/ChatController.java`：
  - `POST /chat/stream` → SseEmitter（事件：`intent`/`delta`/`tool`/`done`/`error`；onTimeout/onError/onCompletion dispose 订阅防泄漏）
  - `GET /conversations`、`POST /conversations`、`GET /conversations/{id}/messages`
- `dto/`：ChatRequest、ConversationVO、MessageVO、ChatEvent；`common/`：统一异常处理

## 5. React+TS 前端（需求 4）

`frontend/` 目录，Vite + React + TS（npm 可用，Node 24）：
- `vite.config.ts`：dev 代理 `/api` → `http://localhost:8080`
- `src/types.ts`（Conversation/Message/ChatEvent）、`src/api/`（fetch 流式解析 SSE + 会话 CRUD）
- 布局：左侧会话列表（新建/切换/历史回显）+ 右侧聊天窗（消息气泡、流式打字机输出、工具调用状态条、意图标签）
- 纯 CSS 无 UI 库，`npm run build` 验证可构建
