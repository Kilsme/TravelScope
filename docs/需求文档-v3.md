### 1.1 v3 核心理念：Agent 资格测试

**Agent 的每一轮推理 = 1 次 LLM 调用 = 烧一次 token**；工具调用是确定性代码，零 token、零等待。因此只有满足以下 ≥2 条的任务才配当 Agent：

1. ✅ 多步推理：下一步依赖上一步结果
2. ✅ 自主选工具：调哪个、调几次、什么顺序自己定
3. ✅ 失败能换路重试

反例：单次固定 API 调用 → 是工具；纯文本变换 → 是普通函数。

**这个原则同时是简历亮点**：面试官最爱问"为什么这里要用 Agent"。能答出"我做过资格评估，单次 API 的活降级为工具、意图识别走三级级联零 Agent 化、单次规划 LLM 调用降约 50%"——体现的是多智能体系统里最稀缺的工程判断力。

## 二、项目概述

### 2.1 项目背景

TravelScope 是一款基于多智能体架构的智能旅游助手。用户一句话提出旅行需求，系统通过**精简的 5 Agent 编排**（master 收口 → Planner 执行 → Reviewer 质检），整合实时数据（火车票/机票/天气/酒店/景点）与知识库（RAG），产出"经过质量验证"的行程方案。固定流程的查询全部走工具层，只有真正需要多步推理的环节（POI 检索筛选、路线调优、质量审阅）才使用 Agent。

### 2.2 项目目标

1. **低成本高吞吐**：三层意图级联让 ~60% 流量零模型调用；单次规划 LLM 调用从 ~8 次降到 ~4 次。
2. **质量验证**：Reviewer 分段审核（POI / 路线 / 预算偏好三段定位），不通过**局部回炉**（≤2 次），未失败段结果缓存复用。
3. **多用户隔离**：userId:sessionId 双键隔离状态、任务工作区、记忆。
4. **可运营可观测**：LLM Gateway 保护模型配额；OTEL 全链路追踪 + 3A 评估。
5. **可演进**：v3 架构与 v2 的 P1/P2 规划（记忆/RAG/评估/Prompter）完全兼容。

### 2.3 用户角色

| 角色         | 说明        | 主要诉求                                                                                      |
| ---------- | --------- | ----------------------------------------------------------------------------------------- |
| 游客用户（user） | 匿名或注册用户   | 查票、查天气、智能规划行程                                                                             |
| 管理员（admin） | 运营/算法工程师  | Token 用量、用户管理、知识文档、评估看板、Prompt 管理                                                         |
| 系统（system） | Agent 编排层 | 5 Agent：travel-master（含需求状态机）+ planning-agent + poi-research + route-optimizer + reviewer |

### 2.4 小白名词表（★ 为 v3 新增/变更）

| 术语              | 一句话解释                                 |
| --------------- | ------------------------------------- |
| ★ Agent 资格测试    | 判断一个活该给 Agent（要推理）还是给工具（一次调用）的标准      |
| ★ 三层级联          | L1 规则 → L2 轻量语义 → L3 LLM 兜底，上层命中就不往下走 |
| ★ 需求状态机         | master 里的一个纯代码组件：记着目的地/天数/预算缺哪项，缺就反问  |
| intake          | 接待员：问清需求，缺哪项问哪项（调代码工具判断），问齐才放行        |
| Planner         | 项目经理：拆任务、直接调工具、派 2 个子 Agent、组装行程      |
| poi-research    | 检索员：RAG+ES 双路找景点，多轮筛选出候选清单            |
| route-optimizer | 排线员：把候选景点排出最顺的顺序，迭代调优                 |

| LLM Gateway     | 模型前的网关：限流/熔断/快慢隔离/降级                  |

## 三、v3 三大核心设计决策

### 3.1 决策一：意图识别零 Agent 化（三层级联）【FR-S01】

**判断依据**：意图识别是分类问题——一次推理出结果、不用调工具、不用循环，不需要 Agent 系统。

```
用户消息
   │
   ▼
L0 会话延续（30 分钟内同会话的短追问 → 直接沿用上次意图，0 计算）
   │ 未命中
   ▼
L1 规则层：正则 / 关键词 / 命令前缀        ~60% 流量  0ms / 0 token / 100% 确定
   │ 未命中 ↓
L2 轻量语义层：qwen-turbo 单标签分类        ~30% 流量  ~300ms / 极低成本
   │ 仍未命中 ↓
L3 LLM 兜底：qwen-plus + JSON Schema      ~10% 流量  ~1s / 正常成本
   （现有 IntentClassifier 退化为这一层）
```

**落点**：升级现有 `IntentRouterMiddleware` 内嵌 L1 规则表 + L2 缓存；`IntentClassifier` 退化为 L3 兜底。L3 判过的长难句每周回流分析一次，固定句式沉淀进 L1 规则表（**规则自生长**，级联命中率随运营上升）。

**收益**：~60% 日常流量（打招呼、明确命令）零模型调用；意图分类平均延迟从 ~1s 降到 ~100ms 量级。

### 3.2 决策二：Worker 资格测试瘦身（5 → 2）【FR-S06/S07】

对 v2 的 5 个 Executor Worker 逐一执行资格测试：

| v2 Worker       | 审判          | 理由                             | v3 归宿                         |
| --------------- | ----------- | ------------------------------ | ----------------------------- |
| weather-worker  | ❌ 降为工具      | 天气 API 返回即结果，无推理               | Planner 直接调 WeatherTool       |
| research-worker | ❌ 降为工具      | 固定关键词查询                        | Planner 直接调 searchPois（高德+ES） |
| hotel-worker    | ❌ 降为工具      | 查询 + 预算过滤是纯代码                  | Planner 直接调 HotelTool + 代码层过滤 |
| poi-worker      | ✅ 保留为 Agent | RAG+ES 双路检索、看召回质量决定换关键词再查，多步推理 | **poi-research**              |
| route-worker    | ✅ 保留为 Agent | 排序→算距离→发现不顺→调整再排，迭代试错          | **route-optimizer**           |

**收益**：每次规划少 3+ 次子 Agent LLM 调用；工具调用零 token 零等待；结果确定性更高（工具不会"幻觉"）。

### 3.3 决策三：Intake 混合形态（保留 Agent + 状态机工具化）【FR-S02】

**判断依据**（资格测试重新打分）：反问打交道的是「人的模糊语言」——用户会答"下周吧，两三个人，穷游"，规则抽取这种话很脆，听懂它恰恰是 LLM 强项；但「判断缺哪项」是纯确定性逻辑，代码最合适。因此职责一分为二：

- **Agent 负责「怎么问、怎么听」**（语言能力）：intake-agent，专门优化反问话术——选择题 + 默认值 + 听不懂换问法；
- **代码负责「缺什么」**（确定性）：TripRequirementState 状态机**下沉为工具**（`get_missing_fields` / `update_requirement_state`），由 intake-agent 调用，判断环节零模型调用。

```
RequirementTools（@Tool，代码）{
  get_missing_fields()       // 缺哪些，纯代码计算，0 模型调用
  update_requirement_state() // Agent 理解用户回答后写回
}
TripRequirementState {
  destination, days, startDate, fromCity, budget, preference, people, special
  status: COLLECTING | DONE | DEGRADED（带默认值放行）
}
```

- master 每轮 PLANNING 意图委派 intake-agent；intake 调 `get_missing_fields` → 缺则反问，用户的回答（可模糊）由 Agent 理解后 `update` 写回；
- 反问策略：能选择题不文本（"国内/国外/还没定"+热门城市按钮）、有默认值自动填（"下周末"）；
- 最多反问 3 轮，仍缺则 DEGRADED 放行并在方案中标注「待确认」；
- 存储：Redis hash `trip:req:{userId}:{sessionId}`，与 Agent 状态同隔离级别；
- **成本再评估**：反问是用户在线对话轮，多 1 次调用的延迟被用户打字时间掩盖；一次规划 1~2 次反问，单次规划子 Agent 调用 ~5 次（v2 约 8+）。

### 4.2 一轮 PLANNING 对话的完整链路（v3）

```
[0] 用户消息
       ▼
[1] ChatService.saveUserMessage
       ▼
[2] LLM Gateway：通过 → 进入；触发限流则排队/降级/拒绝
       ▼
[3] 意图三层级联判定【0 Agent】
       ├─ L0 会话延续命中 → 直接沿用上次意图
       ├─ L1 规则命中（如"/规划"、"帮我安排行程"）→ PLANNING
       ├─ L2 qwen-turbo 单标签 → PLANNING
       └─ L3 qwen-plus 兜底 → PLANNING（仅 ~10% 消息走到这层）
       ▼
[4] ChatService.runAgent 注入 RuntimeContext{userId, sessionId}
       ▼
[5] master 检查 TripRequirementState（需求状态机）
       ├─ 缺字段 → 反问（选择题 + 默认值），更新状态，本轮结束
       ├─ 3 轮仍缺 → DEGRADED：带默认值放行，标注「待确认」
       └─ 完整（或 DEGRADED）→ 继续
       ▼
[6] master 调 create_task_backlog → PlanningGate 四维校验（衣食住行缺维报错重拆）
       ▼
[7] PlanningGate 放行 agent_spawn → planning-agent
       ▼
[8] Planner 执行【本步是 v3 瘦身核心】
       ├─ 直接调工具（0 子 Agent LLM 调用）：
       │     ├─ WeatherTool（和风多天预报，与行程天数对齐）
       │     ├─ HotelTool + 代码层预算过滤
       │     ├─ TransportTool / MCP 12306（大交通）
       │     └─ searchPois 初查（高德 + ES）
       ├─ 同回合并行 spawn 2 个子 Agent（agent_spawn 同步模式）：
       │     ├─ poi-research：RAG(pgvector)+ES 双路 → 筛选 → 换关键词再查 → poi_shortlist.md
       │     └─ route-optimizer：读候选 → 两两算路线 → 就近+开放时间排序
       │          → 发现不顺 → 调整再算（迭代）→ route_plan.md
       └─ 收齐组装 itinerary_draft.md + POI 位置修正
       ▼
[9] Planner spawn reviewer-agent
       ├─ 5 维评分（每维 20 分，≥80 且无单维 <12 通过）
       ├─ 不通过：review_report.md → ReviewerRetryMiddleware 拦截"返回用户"
       │     → 替换为"继续委派 Planner"→ 回 [8]（≤2 次）
       └─ 通过：review_passed.md → master 整合输出
       ▼
[10] SSE 事件流：intent → clarify_question(0-3 轮) → task_* → tool_result×N
                  → agent_status(poi/route 并行) → planner_summary
                  → review_score → delta → done
       ▼
[11] ChatService.persistReply + LLM Gateway 上报 token 用量
       ▼
[12] OtelTraceMiddleware 关闭 span → OTel Collector → 评估器（异步落库）
```

**LLM 调用账（v3 单次完整规划）**：master 编排若干轮（含反问实体抽取 1 次轻量调用）+ Planner 1 + poi-research 1 + route-optimizer 1 + reviewer 1 ≈ **4~5 次**；v2 同流程 ≈ 8+ 次；另有天气/酒店/车票/POI 初查全部 0 LLM 调用（工具直出）。

### FR-S01 意图识别三层级联（L0~L3）【MVP，重写 —— v3 核心变更】

- **描述**：意图识别不使用 Agent，改为代码层级联，上层命中即短路返回。
- **实现要点**：
  - **L0 会话延续**：Redis 记录会话最近意图 + 时间戳；30 分钟内同会话且消息为短追问（<20 字符、含代词）→ 直接沿用，0 计算；

  - **L3 LLM 兜底**：现有 `IntentClassifier`（qwen-plus + JSON Schema）退化为兜底层，仅 ~10% 消息到达；
  - **规则自生长**：L3 判过的长难句每周回流分析，固定句式沉淀进 L1 规则表，级联命中率随运营上升；
  - **全链路埋点**：每层命中率 / 延迟上报 OTEL（FR-S12），供调参。
- **验收标准**：~60% 流量在 L1 零模型调用解决；意图分类平均延迟 < 200ms；L3 比例随运营下降。

### FR-S02 intake-agent —— 需求收集（混合形态）【MVP，重写】

- **实现要点**：

  - 工具：`RequirementTools`（`get_missing_fields` / `update_requirement_state`），状态存 Redis hash（`trip:req:{userId}:{sessionId}`）；

- **验收标准**："下周吧，两三个人，穷游"一次理解成功（天数/人数/预算风格）；3 轮内收不齐不无限纠缠（DEGRADED 放行）；完整需求 0 反问直接放行。

### FR-S06 poi-research Agent —— 双路检索与多轮筛选【MVP，v3 核心 Agent 之一】

- **职责**：拿到目的地 + 天数 + 偏好后，产出高质量景点候选清单。
- **为什么配当 Agent**：召回质量依赖多轮迭代——第一轮 RAG+ES 双路召回不够好时，需要自主决定换关键词、扩城市范围、调过滤条件再查。
- **实现要点**：
  - 注册：`SubagentDeclaration.builder().name("poi-research").maxIters(6)`，SHARED 工作区；
  - 双路检索：pgvector 语义路（RAG，游记攻略知识库）+ ES BM25 关键词路，RRF 融合排序（FR-S11 基础设施）；
  - 筛选逻辑：开放时间与行程匹配、评分门槛、主题相关性、去重；
  - 产出：`poi_shortlist.md`（含每个 POI 的坐标、开放时间、建议游玩时长、推荐理由）。
- **验收标准**：候选 POI 全部有来源（RAG 或 ES 命中记录）；召回不足时可观察到换词重查行为；清单规模与天数匹配（如 2 天 6-8 个）。

### FR-S07 route-optimizer Agent —— 路线顺序迭代调优【MVP，v3 核心 Agent 之二】

- **职责**：把 poi_shortlist 排出地理最顺、时间可行的游览顺序。
- **为什么配当 Agent**：排序 → 算距离 → 发现不顺 → 调整再算，是迭代试错过程。
- **实现要点**：
  - 注册：`SubagentDeclaration.builder().name("route-optimizer").maxIters(6)`，SHARED 工作区；
  - 依据 poi_shortlist 坐标两两调 `getDrivingRoute` / `getTransitRoute`；
  - 优化目标：就近聚类分日、开放时间不冲突、单日总通勤 ≤ 90 分钟；
  - 产出：`route_plan.md`（分日 POI 顺序 + 点间通勤方式与时长）。
- **验收标准**：同日 POI 地理聚簇；无"上午在城东下午跑城西再回城东"的往返；通勤总时长达标。

### FR-S08 Reviewer Agent —— 分段审核与局部回炉【MVP，v3.2 重写】

- **v3 决策**：保留为 Agent（而非单次 LLM-as-a-Judge 调用），因为质检需要**自主调工具核验事实**（如重查两地距离验证"顺路"、重查营业时间验证"可行"），这是资格测试 2/3 条都满足的典型 Agent 任务。
- **v3.2 决策（借鉴补强）**：审核从"整单 5 维评分"升级为**分段审核**——一次 LLM 调用内分三段顺序审，输出结构化分段结论；不通过时**只回炉失败段对应的子任务**（与 FR-S14 结果缓存配合，未失败段直接复用）。效果：错误定位精度逼近参考项目的三级审核（城市级/景区带/行程级），但审核调用只有 1 次。
- **分段审核输出契约**（一次调用，结构化 JSON）：
  ```
  段1 POI 有效性：      pass | fail(哪个 POI、什么问题)      ← 可调工具核验存在性/营业时间
  段2 路线连贯性+时间密度：pass | fail(哪天、哪段不顺、超时多少) ← 可调工具重算距离
  段3 预算+偏好匹配：    pass | fail(超了多少、缺了什么偏好)
  ```
- **5 维评分**（每维 20 分，满分 100，作为分段结论的量化依据）：
  1. 完备性（四维齐全 + 覆盖用户关键诉求）；
  2. 可行性（车次/航班真实、营业时间不冲突——可调工具核验）；
  3. 时间冲突（上一项结束 ≤ 下一项开始）；
  4. 费用预算（总费用 vs 用户预算，偏差 ≤ ±10%）；
  5. POI 合理性（就近、主题一致——可调工具核验距离）。
- 通过阈值：总分 ≥ 80 且无任一维度 < 12；**回炉路由**（v3.2 核心）：
  - 段1 fail → 只回炉 poi-research 换 POI（路线/酒店/天气结果缓存复用）；
  - 段2 fail → 只回炉 route-optimizer 重排（POI 池复用）；
  - 段3 fail → 只回炉 Planner 重新组装/换酒店（POI+路线复用）；
  - 不通过写 `review_report.md`（分段结论 + 每维得分 + 扣分项 + 改进建议）→ ReviewerRetryMiddleware 按段路由回炉（≤2 次），超限带"当前最佳版本（已尽力）"返回；
- 评分模型建议 qwen-max，与主链路 qwen-plus 分离。

### FR-S14 分支级重试与任务结果缓存【MVP，v3.2 新增 —— 借鉴补强①】

- **问题**：v3.1 的回炉是"整个 Planner 重做"——并行子任务里 1 个失败，其余 4 个的好结果全部白烧。参考项目的解法是失败**分支级**重试 + KV 缓存复用未过期结果。
- **实现要点**：
  - Planner 派发的每个子任务产出携带 `task_id + 产出类型 + 时间戳`（写共享工作区文件头部）；
  - `TaskResultCache`（Redis，key=`taskresult:{userId}:{sessionId}:{taskType}`）登记各段产出与有效期：POI 清单 30min / 路线 30min / 天气 10min / 酒店 30min；
  - 回炉/重试入口先查缓存：**命中未过期 → 直接复用；过期或失败段 → 只重跑该子任务**；
  - 与 FR-S08 回炉路由联动：段1 fail 只重跑 poi-research，段2 fail 只重跑 route-optimizer；
  - 用户改需求（如换目的地）→ 按影响面失效对应 key（目的地变更全失效，预算变更只失效酒店/预算段）。
- **验收标准**：段2 fail 回炉时日志可见 `cache_hit=poi_shortlist`（POI 结果复用，未重跑 poi-research）；回炉耗时与 LLM 调用数相比全量重做下降 ≥50%。

### FR-S15 EvalCase 用例库【P1，v3.2 新增 —— 借鉴补强③】

- **问题**：v3.1 只有"Bad Case 库"一句话，没有把 Bad Case 变成回归测试资产的机制。参考项目把典型场景沉淀为 EvalCase，每次变更跑回归。
- **实现要点**：
  - 5 类固定用例（对齐参考项目）：**多城市串联 / 亲子出行 / 严格预算约束 / 地点不存在（纠错）/ 路线过密（时间冲突）**；
  - 每类 2~3 条具体 case（输入消息 + 期望行为断言：如"地点不存在"期望系统指出并给替代建议而非编造）；
  - 触发时机：每次改 Prompt / 调架构 / 换模型后，开发自测跑一遍（可做成 Spring Boot 集测或脚本）；
  - 结果记录：过/不过 + reviewer 分段得分，写入 evaluation_records，趋势进 3A 看板（FR-A04）；
  - 与 Bad Case 库打通：线上踩的坑修复后沉淀为新 EvalCase，用例库自生长。
- **验收标准**：5 类用例全绿才允许合并到主分支；任一用例回退能在合并前拦截。

## 十三、附录 C：对照参考项目（trpc-agent-go）的差距与处置【v3.2 新增】

> 背景：v3.1 定稿后逐项对照参考项目复盘，确认四项我们偏弱的能力，处置原则不变——能低成本追平的补进 MVP，需要线上流量或边际收益低的写入演进规划。

| 1 | 失败处理 | 失败**分支级**重试 + KV 缓存复用未过期结果 | Gateway 整体级降级，回炉全量重做 | ✅ **补进 MVP**：FR-S14 分支级重试 + TaskResultCache |
