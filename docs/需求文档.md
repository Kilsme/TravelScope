## 一、项目概述

### 1.1 项目背景

TravelScope 是一款基于多智能体（Multi-Agent）架构的智能旅游助手。用户用一句话提出旅行需求，系统通过「主 Agent 编排 + 规划子 Agent 执行」的协作模式，整合实时数据（火车票、机票、天气、酒店、景点、市内交通）与知识库信息（RAG），产出可直接执行的行程方案。

### 1.2 项目目标

1. **单点查询秒级响应**：天气、车票、酒店等单点问题直接调工具回答，不绕路规划流程。
2. **复杂规划可靠交付**：多天多要素（衣食住行 + 预算）行程规划走「强制任务拆分 → 子 Agent 执行 → 完成度校验 → 循环补做」闭环，杜绝模型跳步。
3. **多用户安全隔离**：每个用户的主/子 Agent 会话状态、任务工作区、长期记忆互不串扰。
4. **可运营**：管理员可查 Token 用量、管理用户、上传知识文档；后续通过积分体系控制调用成本。

### 1.3 用户角色

| 角色 | 说明 | 主要诉求 |
|---|---|---|
| 游客用户（user） | 匿名或注册用户，通过 Web 前端对话 | 查票、查天气、智能规划行程 |
| 管理员（admin） | 运营人员，通过管理端操作 | Token 用量统计、用户管理、知识文档上传 |
| 系统（system） | Agent 编排层内部角色 | 意图路由、任务拆分、委派、校验、记忆 |

### 1.4 小白名词表

| 术语 | 一句话解释 |
|---|---|
| Agent | 能"自己思考→调工具→再思考"的 AI 程序，像一个会查资料的员工 |
| 主 Agent（travel-master） | 客户经理：接用户消息、判断意图、拆任务、派活、收结果 |
| 子 Agent（planning-agent） | 干活的专家：领任务清单，查天气/车票/酒店，产出行程草案 |
| ReAct 循环 | "推理(Reason) → 行动(Act)"反复交替的执行模式 |
| Middleware（中间件） | 插在 Agent 执行链路上的"关卡"，可在代码层拦截/改写行为 |
| RuntimeContext | 每次调用携带的"工牌"：userId + sessionId，用于多用户隔离 |
| Workspace（工作区） | Agent 的"工位文件夹"，任务清单、记忆、技能都放这里 |
| MCP | 即插即用的外部工具协议（如 12306 火车票查询服务） |
| RAG | 检索增强生成：先查知识库再回答，让答案有据可依 |
| 双路检索 | 向量检索（语义像不像）+ 全文检索（关键词准不准）两路一起查再融合 |
| SSE | 服务器向浏览器持续推送事件流的协议，实现打字机效果 |

## 二、技术底座：AgentScope Java 2.0 框架调研结论

> 本节是需求的技术依据。AgentScope 2.0 定位**企业级分布式智能体框架**，其原生能力与本需求的映射关系如下（详细 API 核验见《多用户记忆与工作区隔离方案.md》）。

### 2.1 双层 Agent 架构

```
┌────────────────────────────────────────────────────┐
│ HarnessAgent（工程化外壳 = 本项目主 Agent 用的形态） │
│  工作区 / 长期记忆 / 压缩 / 子代理编排 / 技能 / 权限 │
│  ┌──────────────────────────────────────────────┐  │
│  │ ReActAgent（推理内核，纯"推理→调工具→回复"循环）│  │
│  └──────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────┘
```

- **ReActAgent**：轻量内核。2.0 起实例完全无状态，单实例可安全并发服务多个 (userId, sessionId)。
- **HarnessAgent**：在内核上以 Middleware + Toolkit 通道叠加工程能力，只叠加不改写。本项目的意图路由（IntentRouterMiddleware）、委派门禁（PlanningGateMiddleware）都是走这条官方扩展通道实现的。

### 2.2 与本需求直接相关的框架能力

| 框架能力 | 机制 | 对应本需求 |
|---|---|---|
| 多租户隔离 | `RuntimeContext{userId, sessionId}` 贯穿状态寻址、工作区路径、KV 命名空间 | 需求 1：用户级会话隔离 |
| Middleware 五段洋葱 | `onAgent / onReasoning / onActing / onModelCall / onSystemPrompt` | 需求 2：代码层强制任务拆分（onActing 拦截 agent_spawn） |
| 子代理编排 | `SubagentDeclaration` + `agent_spawn` 工具 + `WorkspaceMode.SHARED/ISOLATED` | 主/子 Agent 共享工作区协作 |
| 三层状态 | ①调用内 AgentState ②跨调用 Session 持久化 ③长期记忆 MEMORY.md | 需求：三级记忆分层 |
| 抽象文件系统 | Local / Remote(Redis/MySQL) / Sandbox 一行切换 | 工作区物理载体、分布式部署 |
| 模型容错 | `FallbackModel`：主模型失败自动切备用模型 | 后续：模型切换 |
| 事件流 | `streamEvents()` 输出类型化事件（文本增量/工具调用/结果） | SSE 流式对话 |

### 2.3 部署形态演进路线

```
开发期（当前）: InMemoryAgentStateStore + 本地磁盘工作区
      │ 切换 stateStore / filesystem（业务代码零改动）
      ▼
生产期: RedisAgentStateStore + RemoteFilesystemSpec(Redis)
        （任意副本恢复任意用户会话，支持水平扩展）
```

### 3.2 一轮对话的完整链路（服务端时序）

```
用户消息
  │
  ▼
[1] ChatService.saveUserMessage()                    消息落库 PostgreSQL
  │
  ▼
[2] IntentClassifier.classify()                      意图分类（CHAT/TOOL_CALL/PLANNING/RAG）
  │     结构化输出 IntentResult{intent, reason}
  │     失败 → 回退主 Agent 自主路由（鲁棒性）
  ▼
[3] SSE 推送 intent 事件给前端（前端可展示"正在规划行程…"）
  │
  ├─ CHAT      → [4a] 主 Agent 直接对话回答，禁止调工具禁止委派（路由指令）
  ├─ TOOL_CALL → [4b] 主 Agent 调工具（天气/车票/酒店/景点/交通）后回答
  ├─ RAG       → [4c] 知识库可用：双路检索→拼接上下文→回答；不可用：回退直接回答
  │
  └─ PLANNING  → [4d] 强制拆分闭环：
        ① 路由指令注入"请按任务拆分流程处理"
        ② 主 Agent 调 create_task_backlog(sessionId, tasksJson)
           └─ TaskRegistry：JSON 解析 → 写 {userId}/tasks/{sessionId}/task_backlog.md
              → 注册内存容器（PENDING 状态）
        ③ 主 Agent 调 agent_spawn 委派 planning-agent
           └─ PlanningGateMiddleware 在 onActing 拦截：
              未登记清单 → 替换为 planning_gate_hint 纠正指令，委派根本不执行
              （代码层强制，不依赖模型自觉）
        ④ 子 Agent read_file 读 task_backlog.md → 按优先级执行
           每项：update_task_status(IN_PROGRESS→DONE/FAILED) 逐项回报
           写 execution_result.md / itinerary_draft.md
        ⑤ 主 Agent 调 get_task_progress 查完成度
           ├─ 全部 DONE → 读取草案，核验整合，输出最终方案
           └─ 有未完成/失败 → 未超循环上限则重新委派补做（见 FR-S04）
  │
  ▼
[5] 事件流：intent → delta（打字机）→ tool（工具名:状态）×N → done（完整回复）
  │
  ▼
[6] ChatService.persistReply() 保存助手回复
```

## 四、功能需求 —— 用户端

> 优先级：MVP = 本期必须；P1/P2 = 后续迭代。

### FR-U01 火车票实时查询【MVP，已实现】

- **描述**：用户查询两地之间的火车票（车次、时间、余票、价格），数据必须来自 12306 实时接口。
- **实现要点**：MCP 客户端 `12306-mcp`（`AgentConfig.registerMcpClients()`，stdio 模式 `cmd /c npx -y 12306-mcp` 拉起）；相对日期（"明天"）先调 `mcp__c12306__get-current-date` 解析。
- **验收标准**：
  1. 「查一下明天北京到上海的高铁票」10 秒内返回真实车次与余票；
  2. 票价/车次与 12306 返回完全一致，无编造；
  3. MCP 服务不可用时，明确告知查询渠道，不假造数据。

### FR-U02 机票实时查询【MVP，已实现（需配置 Key）】

- **描述**：查询两地航班与实时票价。
- **实现要点**：MCP `variflight`（飞常准），环境变量 `VARIFLIGHT_API_KEY`；未配置时启动告警并跳过注册，不阻断应用。

### FR-U03 实时天气查询【MVP，已实现】

- **描述**：查指定城市实时天气与未来多天预报（3/7/10/15/30 天）。
- **实现要点**：`WeatherTool.getWeather(city)` / `getWeatherForecast(city, days)`，和风天气 API；行程规划时自动纳入穿衣建议。

### FR-U04 酒店与餐饮搜索【MVP，已实现】

- **描述**：按城市/关键词搜酒店；按坐标搜周边 POI（餐饮/商场等）。
- **实现要点**：`HotelTool.searchHotels / searchNearbyPois`，高德 Web API。

### FR-U05 景点信息查询（准确性保障）【MVP，部分实现】

- **描述**：景点名称、地址、评分等信息除高德工具外，须用 RAG 知识库（pgvector 向量 + ES BM25 双路检索）交叉校准，避免单一数据源错误。
- **实现要点**：
  - 双路检索：`travelscope.rag.mode=dual`，向量权重 0.7 / 全文权重 0.3，RRF 融合（k=60），Top-5；
  - 数据链：`document_chunks`（pgvector 1024 维）+ `document_chunks_fulltext`（ES）；
  - 现状：`RagServiceStub` 桩实现（`isAvailable()=false`），配置体系与表结构已就绪，待接 `SimpleKnowledge + PgVectorStore + DashScopeTextEmbedding`。
- **验收标准**：知识库可用时，景点类回答附知识库依据；检索未覆盖部分明确标注，不与工具数据混淆。

### FR-U06 智能行程规划【MVP，已实现核心闭环】

- **描述**：用户提出多天多要素行程需求（如"成都五日游，预算 6000"），系统产出按天组织、时间衔接、含衣食住行的完整方案。
- **实现要点**：见服务端 FR-S02～S05；输出格式为 Markdown（每日时间线 + 交通 + 费用 + 天气穿衣建议 + 预算汇总 + 待确认项）。
- **验收标准**：
  1. 时间线连续（上一项结束 = 下一项开始），跨地点移动写明交通方式与耗时；
  2. 跨城出行必含城际大交通任务（火车票/机票）；
  3. 名称、时间、价格与工具返回完全一致；不确定项标「待确认」。

### FR-U07 流式对话与会话管理【MVP，已实现】

- **描述**：SSE 打字机式回复；多会话创建/切换/历史消息查看；会话标题自动生成。
- **实现要点**：`POST /api/chat/stream`（POST+SSE，支持长消息）；事件序列 `intent → delta/tool ×N → done|error`；`GET /api/chat/conversations`、`POST /api/chat/conversations`、`GET /api/chat/conversations/{id}/messages`。

### FR-U08 关键信息缺失反问【MVP，已实现（提示词层）】

- **描述**：规划需求缺目的地/天数/日期等关键信息时，先向用户反问补齐，一轮最多追问一次，不盲目委派规划。
- **实现要点**：主 Agent 系统提示词第二节 + IntentRouterMiddleware PLANNING 路由指令；升级方向见 FR-S06（代码层校验）。
- **验收标准**：「帮我规划个行程」（无目的地）→ 收到针对性追问而非直接规划。

## 五、功能需求 —— 服务端 Agent 编排

### FR-S01 意图识别与路由（子 Agent / 工具 / 闲聊三分流）【MVP，已实现】

- **描述**：主 Agent 接收消息后，先判定走哪条路径：
  1. **普通聊天（CHAT）**：直接回答，禁工具禁委派；
  2. **单点工具调用（TOOL_CALL）**：天气/车票/酒店/景点/交通等一次工具可答的查询；
  3. **行程规划（PLANNING）**：多天多要素整合 → 走强制拆分闭环委派子 Agent；
  4. **知识问答（RAG）**：攻略/政策/文化类 → 知识库检索后回答（不可用回退直接回答）。
- **实现要点（双层保险）**：
  - 应用层：`IntentClassifier`（轻量 ReActAgent + 结构化输出 `IntentResult`，few-shot 提示词，独立 sessionId `-intent` 后缀不污染主会话）；
  - Agent 层：`IntentRouterMiddleware.onSystemPrompt()` 按意图追加路由指令（如 TOOL_CALL → "禁止委派规划子 Agent"）；
  - 鲁棒性：分类失败返回 null → 主 Agent 按自身提示词自主路由。
- **验收标准**：闲聊与单点查询 100% 不触发 planning-agent；分类服务异常时对话不中断。

### FR-S02 主 Agent 任务拆分 —— 代码层强制（不只写提示词）【MVP，已实现】

- **描述**：主 Agent 对 PLANNING 任务的拆分结果**必须**写入任务容器才算有效；委派子 Agent 前若未登记清单，由代码层直接拦截，模型无法绕过。
- **实现要点**（三层防线）：

| 层 | 组件 | 机制 |
|---|---|---|
| 提示词层 | `TravelMasterAgent.SYS_PROMPT` | 要求先 `create_task_backlog` 再委派（软约束） |
| 工具层 | `TaskTools.create_task_backlog` | 唯一登记入口：解析 tasksJson → 写 MD → 注册内存容器；`get_task_progress` 查进度；`update_task_status` 回报状态 |
| 代码层 | `PlanningGateMiddleware.onActing`（order=-1000，责任链最外层） | 拦截 `agent_spawn`：`TaskRegistry.hasBacklog(userId, sessionId)` 为假 → 把该工具调用**重写**为 `planning_gate_hint` 纠正指令（同 tool_use id 配对），委派根本不执行，ReAct 循环读到纠正结果后自行补登记 |

- **任务清单结构**（task_backlog.md，表格形式）：

```markdown
| 任务ID | 描述 | 建议工具/技能 | 优先级 | 状态 |
|---|---|---|---|---|
| T1 | 查询成都 5 天天气预报 | weather-query | P0 | PENDING |
| T2 | 搜索春熙路周边酒店 | hotel-search | P0 | PENDING |
| T3 | 查询北京→成都高铁票 | train-ticket-query | P0 | PENDING |
| T4 | 检索成都景点知识库校准 | attraction-search | P1 | PENDING |
```

- **验收标准**：构造提示词注入让模型直接 agent_spawn → 委派被拦截且日志出现"委派门禁拦截"；补登记后放行。

### FR-S03 主/子 Agent 共享工作区 + 用户会话双级隔离【MVP，已实现】

- **描述**：每个用户拥有独立工作区 `{workspace}/{userId}/`；每个会话的任务文件隔离在 `{workspace}/{userId}/tasks/{sessionId}/`；同一会话内主/子 Agent 共享该区间协作。
- **实现要点**：
  - `SubagentDeclaration.workspaceMode(SHARED)`：子 Agent 与主 Agent 共享工作区（ISOLATED 会把子 Agent 隔到 `agents/{name}/` 导致读不到任务清单）；
  - `TaskWorkspaceService.getTaskDir(userId, sessionId)`：路径 `Paths.get(workspaceRoot, userId, "tasks", sessionId)`，与 harness 用户目录约定对齐（Agent 相对路径以 `{workspace}/{userId}/` 为根）；
  - `TaskRegistry` 注册键 `userId:sessionId` 双键 `ConcurrentHashMap`，错号/越权一律 ERROR；
  - Agent 侧会话状态：`RuntimeContext{userId, sessionId="conv-{conversationId}"}` 每次调用显式传入（框架按二元组寻址 AgentState）。
- **协作文件协议**：

| 文件 | 写入方 | 读取方 | 用途 |
|---|---|---|---|
| `task_backlog.md` | 主 Agent（经 create_task_backlog） | 子 Agent | 任务清单（含状态追加记录） |
| `execution_result.md` | 子 Agent | 主 Agent | 逐任务执行结果 |
| `itinerary_draft.md` | 子 Agent | 主 Agent | 完整行程草案 |
| `session_meta.md` | 系统 | 系统 | 会话元信息与状态 |

- **验收标准**：用户 A 与用户 B 同时规划 → 互不可见对方任务文件；AgentState 按 (userId, sessionId) 寻址无串台。

### FR-S04 任务完成度判断与循环补做【MVP，工具已实现 / 循环节需强化】

- **描述**：子 Agent 汇报后，主 Agent 须检查任务完成度；存在未完成（PENDING）、执行不仔细或失败（FAILED）的任务时，在循环上限内**重新委派子 Agent 补做**，而非直接交付半成品。
- **实现要点**：
  - 状态机：`PENDING → IN_PROGRESS → DONE / FAILED`（`TaskRegistry.SessionTaskContainer`，`AtomicReference` 保证线程安全）；
  - 进度查询：`get_task_progress` 返回"共 N 项：已完成 x，进行中 y，待处理 z，失败 w + 未完成任务列表"；
  - 循环控制（待强化，当前为提示词层要求主 Agent 主动复查）：建议落地为 **PLANNING 收尾门禁**——主 Agent 产出最终回复前，若 intent=PLANNING 且 `get_task_progress` 存在非 DONE 任务且循环次数 < 上限（建议 2 次），由 Middleware 注入"仍有未完成任务，请继续委派补做"指令；超上限则在回复中如实列明未完成项与原因。
- **验收标准**：人为让某工具持续失败 → 最终方案中该项标注「待确认/失败原因」，其余任务不受影响；修复后重新委派可补全。

### FR-S05 衣食住行四维规划模板【MVP，部分实现（提示词层）】

- **描述**：行程规划的任务拆分与草案生成必须覆盖四个维度，缺项视为拆分不合格：
  - **行**：城际大交通（火车/机票，跨城必含）+ 市内交通（路线/耗时）；
  - **住**：住宿推荐（位置理由 + 预算档位）；
  - **食**：每日餐饮推荐（周边 POI 餐饮检索）；
  - **衣**：天气预报 + 穿衣建议。
- **实现要点**：当前由主 Agent 提示词（拆分要求"跨城出行必须包含城际大交通任务"）+ 子 Agent 草案格式（末尾天气穿衣建议）保障；**升级方向**：`TaskRegistry.createBacklog` 增加四维覆盖校验（代码层：任务描述关键词/任务类型标记含 transport/hotel/food/weather 四类），缺维返回 ERROR 要求重拆——与 FR-S02 同一套强制机制。
- **验收标准**：规划结果必含四维信息；预算汇总与各项费用一致。

### FR-S06 信息确认反问（代码层强化）【P1】

- **描述**：PLANNING 意图但缺关键要素（目的地/天数/日期/出发城市）时，在代码层拦截委派并强制反问，而非仅靠提示词。
- **实现要点（规划）**：扩展 `PlanningGateMiddleware`——拦截 agent_spawn 时除校验清单登记外，再校验 `PlanningTask` 列表是否包含必需四要素（可由 create_task_backlog 附带 `requirements` 字段承载）；缺失则替换为反问指令工具结果，主 Agent 转向用户追问。

### FR-S07 三级记忆分层【P1（框架已内置，待启用配置）】

- **描述**：Agent 记忆按三层组织（对齐 AgentScope 2.0 三层状态模型）：

| 层 | 内容 | 生命周期 | 本项目落地 | 现状 |
|---|---|---|---|---|
| L1 调用内状态 | 当前 ReAct 循环的上下文、权限、工具状态 | 单次调用 | RuntimeContext + AgentState | ✅ 已实现（InMemory） |
| L2 跨调用会话状态 | 同 sessionId 的完整对话历史、任务进度 | 会话级持久化 | AgentStateStore（升级 Redis）+ 应用侧 messages 表 | ⚠️ 部分（重启丢失 / DB 有备份） |
| L3 长期记忆 | 用户偏好、历史行程事实沉淀 | 跨会话累积 | Workspace `MEMORY.md` + `memory/YYYY-MM-DD.md`，每轮注入 system prompt | ❌ 未启用 |

- **实现要点（规划）**：
  1. 启用压缩与记忆：`HarnessAgent.builder().compaction(CompactionConfig.builder().triggerMessages(50).keepMessages(20).build())`（压缩前自动抽取事实 → 每日流水 → 后台合并去重 → MEMORY.md，每轮按 8000 token 预算注入）；
  2. 状态外置：`RedisAgentStateStore`（keyPrefix `travelscope:session:`）替换 InMemory，多副本可恢复；
  3. 隔离：`IsolationScope.USER`（同一用户跨会话共享偏好记忆）；文件命名空间 `{userId}/`。
- **验收标准**：用户说过"不吃辣" → 新会话推荐餐饮时自动规避；服务重启后对话可续。

### FR-S08 RAG + ES 双路检索（景点信息准确性）【P1】

- **描述**：知识型问题与景点校准走双路检索：
```
用户查询
  ├─ 向量检索：pgvector kNN（text-embedding-v3，1024 维）── 语义相似
  └─ 全文检索：Elasticsearch BM25 ──────────────────────── 关键词精确
                    │
                    ▼ RRF 融合（k=60，向量 0.7 / 全文 0.3）
                 Top-5 片段 → 拼入上下文 → 回答（标注来源）
```
- **实现要点（规划）**：替换 `RagServiceStub` 为真实现（`SimpleKnowledge + PgVectorStore + DashScopeTextEmbedding` + ES 客户端），ChatService 的 RAG 分支零改造接入；文档入库链路见 FR-A03。
- **验收标准**：双路召回率 > 单路；景点名称/地址与知识库一致；检索为空时明确说明并回退。

### 8.2 P1 迭代（紧接 MVP）

1. **RAG 双路检索落地**（FR-S08 + FR-A03 文档入库）——景点准确性的关键。

4. **管理端 MVP**（FR-A01~A03）：token 统计、用户管理、文档上传。

### 8.3 P2 迭代（生产化强化）

1. **缓存**：Redis 缓存工具查询结果（天气 10min / POI 1h / 车票不缓存），降低外部 API 压力与 token 消耗。
2. **MQ**：文档解析入库异步化（上传 → 发消息 → 消费者分块嵌入）；后续可扩展行程生成任务的异步化。
3. **模型切换**：意图分类用 qwen-turbo（省钱）+ 主链路 qwen-plus + 复杂规划可切 qwen-max；`FallbackModel` 主备容错（主模型限流自动切换备用）。
4. **优雅报错**：错误分类（模型超时/工具失败/外部 API 限流/内容审核）→ 差异化用户文案 + 自动降级（备用模型/缓存数据）+ 告警。
5. **限流（JUC 并发包）**：
   - 总体限流：全局 `Semaphore`（如并发 50）保护下游 DashScope/高德配额；
   - 局部限流：每用户独立 `Semaphore`（如并发 2）+ 单用户 QPS 窗口，防单用户刷爆；
   - 意图分类器并发上限独立控制。
6. **积分体系**：签到领积分 → token 调用按积分计费（对话/规划分级扣费），实现成本自运营：
```
签到(sign-in) → 积分入账(points_ledger) → 对话请求 → 余额校验/冻结 → 扣费 → 回复
                     ▲ 积分过期/活动加成（运营配置）
```

### 8.4 P3（远期）

沙箱文件系统（DockerFilesystemSpec）隔离工具执行；OpenTelemetry 全链路追踪；多副本水平扩展（DistributedStore 一键分布式装配）。
