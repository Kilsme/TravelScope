## 一、项目现状速览

### 1.1 已实现的架构

```
Vue 3 前端（frontend/）
   │ HTTP + SSE
   ▼
ChatController ──► ChatService（对话编排）
   │                  │
   │                  ├─ IntentClassifier（轻量 ReActAgent，结构化意图分类）

   ▼
```

### 1.2 与隔离相关的现状对照

| 维度            | 现状                                                    | 评价                  |
| ------------- | ----------------------------------------------------- | ------------------- |
| 会话寻址          | `RuntimeContext{userId, sessionId="conv-"+id}` 每次调用都传 | ✅ 正确，多用户/多会话寻址已就绪   |
| 会话状态存储        | `InMemoryAgentStateStore`                             | ⚠️ 重启即丢，仅支持单进程      |

| 主/子 Agent 工作区 | `WorkspaceMode.SHARED` 共享工作区                          | ✅ 符合 MD 任务区间协作设计    |
| 手写任务区间        | `TaskWorkspaceService` 按 `tasks/{sessionId}` 分目录      | ✅ 思路正确，但目前无调用方      |

## 二、AgentScope 2.0 的隔离机制（调研结论）

框架把「隔离」拆成三个正交的层，分别由不同组件负责——这是理解多用户开发的关键：

```
┌─────────────────────────────────────────────────────────────┐
│ 层 1：会话状态 AgentState（对话历史、压缩摘要、权限、Plan 状态） │
│   组件：AgentStateStore                                      │
│   寻址：(userId, sessionId) 二元组 —— 每次 call() 由          │
│         RuntimeContext 传入                                   │
│   后端：InMemory / JsonFile(默认) / Redis / MySQL / OSS       │
├─────────────────────────────────────────────────────────────┤
│ 层 2：长期记忆（MEMORY.md + memory/YYYY-MM-DD.md 事实流水）    │
│   组件：Workspace 内文件 + MemoryFlushMiddleware + 压缩合并    │
│   隔离：IsolationScope（SESSION/USER/AGENT/GLOBAL）分桶        │
│   可选后端：mem0（Mem0LongTermMemory，core 内置客户端）        │
├─────────────────────────────────────────────────────────────┤
│ 层 3：工作区文件（AGENTS.md/skills/subagents/agents/<id>/...） │
│   组件：FilesystemSpec（Local / Remote / Sandbox）            │
│   隔离：IsolationScope → NamespaceFactory 路径/KV 前缀         │
│   子 Agent：WorkspaceMode.SHARED / ISOLATED                   │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 层 1：AgentState 按 (userId, sessionId) 寻址

- `HarnessAgent` 单例无状态，可并发服务所有用户；**每次 `call()`/`streamEvents()` 必须传 `RuntimeContext{userId, sessionId}`**，不传则所有请求共享 `defaultSessionId` 导致串台（本项目已正确传入）。
- 多租户技巧：把租户/Agent 维度折进字符串，如 `userId(tenantId + ":" + userId)`、`sessionId(agentId + ":" + sessionId)`。
- 后端选型：

| 实现                        | 模块               | 适用                                                                    |
| ------------------------- | ---------------- | --------------------------------------------------------------------- |
| `InMemoryAgentStateStore` | core             | 单元测试，进程退出全丢                                                           |
| `JsonFileAgentStateStore` | core             | **单机开发默认**（不显式设置 stateStore 即此项），根目录 `~/.agentscope/state/<agentId>/` |
| `RedisAgentStateStore`    | extensions-redis | **多副本生产首选**（Jedis/Lettuce/Redisson）                                   |
| `MysqlAgentStateStore`    | extensions-mysql | 需要审计/联表查询                                                             |

```java
// 生产：Redis 状态存储
AgentStateStore stateStore = RedisAgentStateStore.builder()
        .jedisClient(new JedisPooled("redis://localhost:6379"))
        .keyPrefix("travelscope:session:")
        .build();
```

### 2.2 层 2：长期记忆

工作区内的两层结构：

```
workspace/
├── MEMORY.md            ← 策划后的长期事实，每轮注入 system prompt 的 <memory_context> 段
└── memory/
    └── YYYY-MM-DD.md    ← 每日追加的事实流水（压缩前由 MemoryFlushMiddleware 抽取）
```

- 写入：对话压缩前抽取新事实 → 追加到当日文件 → 后台节流合并去重 → 重写 `MEMORY.md`。
- 读取：每轮注入，受 `maxContextTokens`（默认 8000）预算约束，超出截断并引导模型用 `memory_search` 工具查老内容。
- 启用方式（jar 已核验，类在 harness 包）：

```java
import io.agentscope.harness.agent.memory.compaction.CompactionConfig;

HarnessAgent.builder()
    .compaction(CompactionConfig.builder()
            .triggerMessages(50)   // 累计 50 条消息触发压缩
            .keepMessages(20)      // 压缩后保留最近 20 条原文
            .build())
    .build();
```

- `LongTermMemoryMode` 三态（jar 已核验）：`AGENT_CONTROL`（Agent 自主读写）/ `STATIC_CONTROL`（静态注入）/ `BOTH`。
- 可选 mem0 后端：`io.agentscope.core.memory.mem0.Mem0LongTermMemory`（core 内置），适合跨 Agent 共享的语义化记忆检索。

### 2.3 层 3：工作区与 IsolationScope

`IsolationScope`（jar 已核验：`SESSION / USER / AGENT / GLOBAL`，含 `toNamespaceFactory()`）决定文件命名空间分桶：

| Scope             | 含义               | 本项目适配场景                  |
| ----------------- | ---------------- | ------------------------ |
| `SESSION`         | 每个 sessionId 独立桶 | 一次性规划任务的工作产物             |
| `USER`（Remote 默认） | 同一 userId 跨会话共享  | **用户级长期记忆、个人偏好** ← 本项目应选 |
| `AGENT`           | Agent 内所有用户共享    | 公共知识库（旅游攻略库）             |
| `GLOBAL`          | 全局一桶             | 慎用                       |

- **静态资产覆盖**：`RuntimeContext.userId="alice"` 时，框架优先读 `<userId>/skills/`、`<userId>/subagents/` 覆盖公共版本——可做用户级个性化技能。
- Filesystem 三种模式：
  - `LocalFilesystemSpec`（默认）：本机磁盘 + shell，单进程开发
  - `RemoteFilesystemSpec`：共享 KV（Redis `RedisStore` / MySQL `JdbcStore`），多副本共享长期记忆
  - `SandboxFilesystemSpec`（Docker/K8s/E2B/AgentRun）：不可信代码执行
- 一键分布式装配：`DistributedStore`（`RedisDistributedStore.fromJedis(jedis)` / `MysqlDistributedStore.create(ds)`）自动注入 stateStore + baseStore + 快照 + 执行锁。

### 2.4 子 Agent 工作区：SHARED vs ISOLATED

- `ISOLATED`（默认）：子 Agent 隔离到 `agents/{name}/` 子目录，读写互不影响——适合多个互不相关的专职子 Agent。
- `SHARED`：与父 Agent 同一工作区——本项目已选，因为主 Agent 写的 `task_backlog.md` 需要子 Agent 直接可读。

## 三、多用户记忆隔离：本项目的开发方案

### 3.1 三层记忆模型落地

```
用户 Alice（userId=1）                     用户 Bob（userId=2）
│                                          │
├─ 会话 conv-101 ─┐                        ├─ 会话 conv-102 ─┐
│  AgentState     │  ← (1,"conv-101") 寻址 │  AgentState     │  ← (2,"conv-102") 寻址
│  (对话历史)      │    存 AgentStateStore   │  (对话历史)      │    互不可见
├─ 会话 conv-105 ─┘                        └─ 会话 conv-107 ─┘
│                                          │
├─ 长期记忆 MEMORY.md（USER 桶：users/1/）   ├─ 长期记忆 MEMORY.md（USER 桶：users/2/）
│  「带孩子出行、预算敏感、不吃辣」            │  「喜欢徒步、摄影」
│                                          │
└─ 应用侧：conversations/messages 表        └─ 应用侧：conversations/messages 表
   （按 user_id 外键隔离，已实现）              （已实现）
```

### 3.2 改造步骤（按优先级）

**P0：会话状态持久化（改动最小）**

```java
// AgentConfig.travelMasterAgent() 中：
// 单机阶段：直接删掉 .stateStore(new InMemoryAgentStateStore())，
// 框架默认 JsonFileAgentStateStore（~/.agentscope/state/<agentId>/），重启不丢
// 生产阶段：换 Redis（pom 中 extensions-redis 依赖已引入）
.stateStore(RedisAgentStateStore.builder()
        .jedisClient(new JedisPooled(redisUri))
        .keyPrefix("travelscope:session:")
        .build())
```

**P1：启用长期记忆 + USER 级隔离**

```java
HarnessAgent agent = HarnessAgent.builder()
    // ... 现有配置 ...
    .compaction(CompactionConfig.builder()
            .triggerMessages(50).keepMessages(20).build())
    // 单机：Local 模式下 userId 也会折算成路径前缀（users/<userId>/...）
    // 生产：Remote 共享存储 + USER 隔离
    .filesystem(new RemoteFilesystemSpec()
            .isolationScope(IsolationScope.USER)
            .anonymousUserId("_default"))   // 系统任务等无 userId 场景的兜底桶
    .distributedStore(redisDistributedStore) // 一键注入 stateStore + baseStore
    .build();
```

效果：Alice 的偏好（如「带孩子」「不吃辣」）只写入 `users/1/MEMORY.md`，Bob 的会话中不会注入。**注意：IsolationScope 上线前定好，中途改 scope 等于换命名空间，旧数据不会迁移。**

**P2：个性化增强（可选）**

- 用户级技能覆盖：在 workspace 下放 `<userId>/skills/<name>/SKILL.md` 即可覆盖公共技能（如给 VIP 用户更强的规划技能）。
- 语义记忆检索：接入 `Mem0LongTermMemory`，让 Agent 主动 `memory_search` 用户历史偏好（如「上次去成都住的哪家酒店」）。

### 3.3 应用侧隔离（已实现，保持）

- `conversations` / `messages` 表按 `user_id` 外键隔离，ChatController 层已做归属校验。
- IntentClassifier 调用也传了相同的 `(userId, sessionId)`，意图分类的多轮上下文同样按用户隔离。

## 四、多 Agent 工作区隔离：本项目的开发方案

### 4.1 当前只有 1 主 1 从，但有 3 个隔离问题要面对

**问题 1：多用户并发时，SHARED 工作区里的任务文件会串台**

主 Agent 与 planning-agent 共享工作区，若都把任务清单写到固定文件名（如 `task_backlog.md`），两个用户同时规划时会互相覆盖。

方案（沿用 `TaskWorkspaceService` 的思路，按会话分目录）：

```
.agentscope/workspace/
└── tasks/
    ├── conv-101/            ← Alice 的规划任务区间
    │   ├── task_backlog.md      （主 Agent 写）
    │   ├── execution_result.md  （规划师写回）
    │   └── itinerary_draft.md   （规划师生成的草案）
    └── conv-102/            ← Bob 的规划任务区间（互不干扰）
```

落地动作：把 `TaskWorkspaceService` 注册为 Agent 工具（或在主/规划 Agent 的系统提示词中约定「任务文件一律写入 `tasks/{sessionId}/` 子目录」，Agent 用内置 `read_file`/`write_file` 按路径读写）。后者更符合 Harness「工作区即协作媒介」的设计，推荐。

**问题 2：主 Agent 的静态资产 vs 子 Agent 的运行时产物**

```
workspace/
├── AGENTS.md / skills/ / knowledge/     ← 静态资产（工程师维护，git 管理）
├── MEMORY.md / memory/                  ← 长期记忆（按 USER 桶隔离）
├── tasks/{sessionId}/                   ← 主/子 Agent 协作区（SHARED 模式，按会话分目录）
└── agents/
    ├── travel-master/sessions/          ← 主 Agent 运行时日志（框架自动维护）
    └── planning-agent/                  ← ISOLATED 模式下子 Agent 的独立根（本项目未用）
```

**问题 3：未来扩展更多子 Agent（如「预算核算师」「攻略检索师」）时的隔离策略**

| 子 Agent 性质                 | 建议 WorkspaceMode                                              | 理由                               |
| -------------------------- | ------------------------------------------------------------- | -------------------------------- |
| 需要读主 Agent 任务清单/写回结果（如规划师） | `SHARED`                                                      | 协作媒介在同一个文件树                      |
| 独立作业、只返回结论（如预算核算）          | `ISOLATED`                                                    | 防止其文件污染主工作区，产出经 `task_output` 回传 |
| 用户可直接对话的暴露型子 Agent         | `ISOLATED` + `exposeToUser(true)` | 独立会话状态，注册表由 distributedStore 托管  |

### 4.2 生产环境的工作区部署形态

单机开发（现阶段）：

```java
.workspace(".agentscope/workspace")          // LocalFilesystemSpec 默认
// 不配 stateStore → JsonFileAgentStateStore，重启不丢
```

多副本生产：

```java
DistributedStore store = RedisDistributedStore.fromJedis(new JedisPooled(redisUri));
HarnessAgent.builder()
    .workspace(workspace)
    .distributedStore(store)                  // stateStore + baseStore + 快照 + 锁
    .filesystem(new RemoteFilesystemSpec()
            .isolationScope(IsolationScope.USER)
            .anonymousUserId("_default"))
    .build();
```

> 校验规则（框架强制）：配了 `RemoteFilesystemSpec` 却不换分布式 stateStore → `build()` 直接抛 `IllegalStateException`，防止把会话状态留在 pod 本地盘。

## 六、整体链路

### 6.1 单点查询链路（意图 CHAT / TOOL_CALL）

```
用户「北京今天天气怎么样」
  → POST /chat（SSE）
  → ChatService.streamChat()
      ① 持久化用户消息（messages 表）
      ② IntentClassifier.classify(msg, userId, "conv-101") → TOOL_CALL
      ③ SSE 推送 intent 事件
      ④ travelMasterAgent.streamEvents(msg, ctx)
          IntentRouterMiddleware：非 PLANNING → 禁止委派，主 Agent 直接调 WeatherTool
      ⑤ 事件流过滤（只透传主 Agent 事件）→ SSE delta/tool 事件
      ⑥ 完成 → 持久化助手回复 → SSE done
```

### 6.2 行程规划链路（意图 PLANNING）

```
用户「帮我规划北京三日游，预算3000」
  → ChatService（同上 ①②③）
  → travelMasterAgent.streamEvents(msg, ctx)
      ① IntentRouterMiddleware 放行委派
      ② 主 Agent 任务拆分 → 写 tasks/conv-101/task_backlog.md
      ③ agent_spawn("planning-agent") 委派
            planning-agent（SHARED 工作区，maxIters=8）
              ├─ 读 task_backlog.md
              ├─ 调工具：getWeatherForecast / searchAttractions / searchHotels
              │        / 12306-mcp / variflight-mcp / getTransitRoute ...
              ├─ 写 execution_result.md（逐任务）
              └─ 写 itinerary_draft.md（三日行程草案）
      ④ 主 Agent 读回结果 → 整合润色 → 流式输出给用户
  → SSE 推送 → 持久化回复
```

### 6.3 多用户并发链路（隔离生效点标注）

```
Alice: conv-101 ─┐
                 ├─→ 同一个 travelMasterAgent 单例（无状态，可并发）
Bob:   conv-102 ─┘
        │
        ├─ AgentState：按 (userId, sessionId) 分槽     ← 会话互不串台
        ├─ 长期记忆：按 IsolationScope.USER 分桶        ← 偏好互不泄露
        ├─ 任务文件：tasks/{sessionId}/ 分目录          ← 规划产物互不覆盖
        └─ 应用数据：conversations.user_id 外键         ← 历史互不可见
```

## 七、落地路线建议

| 阶段     | 动作                                                          | 收益         |
| ------ | ----------------------------------------------------------- | ---------- |

| P2     | Redis DistributedStore + RemoteFilesystemSpec(USER)         | 多副本生产化     |
| P2     | mem0 / Plan Mode / 更多子 Agent                                | 体验增强       |
