## 二、项目概述

### 2.1 项目背景

TravelScope 是一款基于多智能体（Multi-Agent）架构的智能旅游助手。用户用一句话提出旅行需求，系统通过 **Intake-Execute-Review 三阶段多 Agent 编排**，整合实时数据（火车票、机票、天气、酒店、景点、市内交通）与知识库信息（RAG），产出"经过质量验证"的行程方案。

### 2.2 项目目标

1. **一次成型信息收集**：用户无需多轮被动追问，Intake Agent 主动维护需求完整性。
2. **并行执行 + 质量验证**：Executor Team 并行拉取数据，Reviewer 把关产出质量，不合格自动回炉。
3. **多用户安全隔离**：每个用户的 Intake/Executor/Reviewer 会话状态、任务工作区、长期记忆互不串扰。
4. **可运营可观测**：LLM Gateway 限流/熔断保护资源；OpenTelemetry 全链路追踪 + 3A 评估让问题可定位、效果可量化。
5. **Prompt 可持续优化**：通过 Prompter 闭环自动调优，越用越好。

### 2.3 用户角色

| 角色 | 说明 | 主要诉求 |
|---|---|---|
| 游客用户（user） | 匿名或注册用户 | 查票、查天气、智能规划行程 |
| 管理员（admin） | 运营/算法工程师 | Token 用量、用户管理、知识文档、**评估看板、Prompt 管理** |
| 系统（system） | Agent 编排层 | **三阶段**：Intake 收口 → Executor Team 并行执行 → Reviewer 质量把关 |

### 2.4 小白名词表（新增条目标 ★）

| 术语 | 一句话解释 |
|---|---|
| Intake Agent | 接待员：主动问清楚用户需求，直到信息齐了才放行 |
| Executor Agent Team | 执行班：多个并发干活的人（查景点/查路线/查住宿） |
| Planner | 项目经理：把执行班的结果组装成完整行程方案 |
| Reviewer Agent | 质检员：检查行程是否合理，不合格打回重做 |
| **★ 3A 评估** | Availability（可用率）/ Accuracy（准确率）/ Affordability（性价比）三维评估 |
| **★ Bad Case 重放** | 把历史上答得差的对话重跑一遍，验证改进是否生效 |
| **★ Prompter 闭环** | Trace → Bad Case → 自动改 Prompt → 灰度上线 → 评估 → 再迭代 |
| **★ LLM Gateway** | 模型前的"网关"，限流/熔断/快慢隔离/降级，护住下游模型配额 |
| **★ 快慢隔离** | 慢调用单独泳道，避免一条慢请求拖垮整体 |

## 三、对照参考：trpc-agent-go 项目的关键设计借鉴

> 以下要点是 v2 编排演进的直接灵感来源，本项目将其落到 Java/AgentScope 生态：

### 3.1 Intake-Execute-Review 三阶段

```
用户消息
   │
   ▼
[Intake]    收集完整需求（多轮反问 + 选择题 + 默认值 + 状态机）
   │ 完整？
   ▼ 是
[Execute]   并行 Agent Team（Research/POI/Route/Weather/Hotel）
            + Planner 整合（含 POI 优化、路线纠错、POI 位置修正）
   │
   ▼
[Review]    评分 5 维（完备性/可行性/时间冲突/费用预算/POI 合理性）
   │ 通过？
   ▼ 否 ──────────► 回 Executor 重做（受最大重试次数约束）
   │
   ▼ 是
返回用户
```

### 3.2 Agent Team 并行

```
Planner
  │
  ├── Research Agent（并行） ─── POI/攻略知识库检索
  ├── POI Agent（并行）    ─── 高德 POI 检索 + RAG 校准
  ├── Route Agent（并行）  ─── 高德路线规划
  ├── Weather Agent（并行）─── 和风天气多天预报
  └── Hotel Agent（并行）  ─── 高德酒店检索
        │
        ▼ 汇总
      Planner：组装 itinerary + POI 顺序调优 + 跨点路线纠错
```

### 3.3 Trace & Evaluation + Prompter 闭环

```
生产流量 ──► Agent 编排 ──► OTEL 埋点 ──► Trace/Prom 收集器
                                       │
                                       ▼
                          评估器（LLM 评分 + 静态规则 + 人工复审）
                                       │
                                       ▼
                              Bad Case 库（按类型聚类）
                                       │
                                       ▼
                            Prompter 自动改 Prompt 三类
                  （System / Few-shot / Tool description）
                                       │
                                       ▼
                              灰度评估 → 晋升正式版本
```

## 四、技术底座：AgentScope 2.0 能落地的对应机制

| 借鉴点 | trpc-agent-go 实现 | AgentScope Java 2.0 对应 | 备注 |
|---|---|---|---|
| Intake Agent | 单 Agent + 状态机 | **SubagentDeclaration**（intake-agent） + 状态存 `InMemoryAgentStateStore`/Redis | Intake 状态用 AgentState 而非 MD 文件 |
| Executor Team 并行 | goroutine 并发 | **Background subagent** + `agent_spawn` 异步模式；多 subagent 同步发起 | AgentScope 支持异步/同步 |
| Reviewer 自循环 | 自调 Executor | **onAgent Middleware**：Reviewer 评分 < 阈值时把"返回用户"事件替换为"重做"指令 | 复用 FR-S02 同款拦截机制 |
| 共享工作区 | 工作目录 | **WorkspaceMode.SHARED**（已用） | 不变 |
| Trace & Eval | 自实现 OTEL | **AgentScope 默认 OTEL 埋点** + `streamEvents()` 28 类事件 | 仅需接 Collector + 评估器 |
| Prompter 闭环 | 自研脚本 | 字符串 Prompt 替换为 **PromptVersion Registry**，LLM 辅助改写 + 灰度路由 | 框架无关 |
| LLM Gateway | 自实现熔断 | **`ReActAgent.Builder.fallbackModel(...)`**（原生备用模型）+ `ExecutionConfig`（超时/重试/退避，见 `io.agentscope.core.model.ExecutionConfig`）+ 自定义 RateLimiter Middleware | 限流建议在应用层用 `Semaphore`/`Resilience4j`；核验自 agentscope-core 2.0.3 jar |
| 三级记忆 | - | **compaction + MEMORY.md**（不变） | 不变 |

### FR-U06 智能行程规划【MVP，v2 升级到 Intake-Execute-Review】

- **升级要点**：用户说一句，Intake Agent 主动追问补齐 → Planner 并行拉取 → Reviewer 质量把关；最终方案"经过质检"。
- **验收标准**（在 v1 基础上新增）：
  1. **质检通过标记**：方案末尾显示"✅ 已通过质量审阅（评分 x/100）"；
  2. **可查看审阅报告**：用户可点击"查看质检详情"，展开 review_report.md 的 5 维评分明细；
  3. **方案承诺**：POI 顺序最优、跨日路线无时间冲突、预算偏差 ≤ ±10%、高德坐标位置已核验。

### FR-U07 流式对话与会话管理【MVP，已实现】

### FR-U08 关键信息反问【MVP，v2 升级为 Intake 多轮交互】

- **升级要点**：从"一轮最多追问一次"提示词约束 → Intake Agent 维护需求状态机，支持"选择题 + 默认值"降低用户负担，最多反问 5 轮仍不完整则带已知信息继续（标注「待确认」）。
- **验收标准**：缺少目的地时 Intake 给出"国内/国外/还没定"+热门城市下拉选项；用户点选即可，比纯文本追问节省 50% 交互时间。

### FR-U09（v2 新增）方案可调优【P1】

- **描述**：Reviewer 不通过时，用户不必手动介入；系统在后台自动重做并在完成后通知用户（"我们又优化了一版"）。
- **验收标准**：Reviewer 重做 ≤ 2 次后必须给用户一个最终版本，无论评分。

### FR-S09（v2 新增）Intake Agent —— 一次成型需求收集【MVP】

- **描述**：用户提出规划需求时，由 Intake Agent 专门负责把需求信息收集完整（目的地/天数/出发城市/日期/预算/偏好/人数/特殊要求），收齐后才放行到 Executor。
- **实现要点**：
  - 注册：`SubagentDeclaration.builder().name("intake-agent").inlineAgentsBody(...)`；
  - 状态机：`IntakeStateStore`（按 userId+sessionId 隔离），内存 + 持久化双写，结构字段：
    ```
    IntakeState { destination, days, fromCity, startDate, endDate, budget, preference,
                   people, specialRequirements, missingFields, status: COLLECTING|DONE|TIMEOUT }
    ```
  - 反问策略：
    1. **优先级**（destination > days > dates > fromCity > budget > preference > special）；
    2. **交互方式**：能选择题不文本（如"国内/国外/还没定"+ 热门城市按钮）；有默认值自动填（如"今天/明天/下周"）；
    3. **兜底**：连续 5 轮仍未收齐 → 标注"待确认"放行，不无限追问；
    4. **退出条件**：`missingFields.isEmpty()` → 写 `intake_done.md` + 返回"信息已收齐"。
- **验收标准**：完整需求 0 反问直接进入 Executor；缺 1 字段给选择题 + 默认值；缺 3 字段以上用 Intake 多轮引导；最终无论收齐与否都释放给 Executor。

### FR-S10（v2 新增）Executor Agent Team —— 并行执行【MVP】

- **描述**：Planner 把任务拆给 5 类 Worker 并行执行，最后汇总组装。
- **实现要点**：
  - Worker 注册：5 个 `SubagentDeclaration`（research/poi/route/weather/hotel），每个 `maxIters=4`（Worker 单工具职责，迭代少），`WorkspaceMode.SHARED`；
  - 并行触发：Planner 在一次推理回合内**同时**发出 5 个 `agent_spawn`（框架原生支持同步/异步两种模式与独立超时：`AgentSpawnTool.agentSpawn(ctx, state, name, task, ..., timeoutSeconds, syncMode)`，API 已核验自 agentscope-harness 2.0.3 jar），同步模式下阻塞收齐 5 个 Worker 结果；
  - POI 优化（Planner 内）：根据地理坐标 + 开放时间 + 主题相关性排序；
  - 路线纠错：跨日跨点两两做 `getDrivingRoute`/`getTransitRoute`，检测总时长 > 用户预期时改 POI 顺序；
  - POI 位置修正：Worker 返回 POI 用反向地理编码核验，坐标偏差 > 50m 时重新 `geocode`；
  - 写回 `itinerary_draft.md`。
- **验收标准**：5 个 Worker 并行，5 工具调用同回合触发；规划结果 POI 顺序优化 + 路线无时间冲突 + POI 坐标已核验。

### FR-S11（v2 新增）Reviewer Agent —— 质量审阅与自循环【MVP】

- **描述**：对 `itinerary_draft.md` 做 5 维评分，不通过回炉 Executor 重做，通过才放行返回用户。
- **实现要点**：
  - 5 维评分（每维 20 分，满分 100）：
    1. **完备性**（是否含四维 + 是否覆盖用户提到的关键诉求）；
    2. **可行性**（车次/航班是否真实、营业时间是否冲突）；
    3. **时间冲突**（每项起止时间是否连续、上一个结束 ≤ 下一个开始）；
    4. **费用预算**（总费用 vs 用户预算，偏差 ≤ ±10%）；
    5. **POI 合理性**（POI 顺序是否符合地理位置就近、主题一致）。
  - 通过阈值：总分 ≥ 80 且无任一维度 < 12；
  - 不通过：写 `review_report.md`（含每维得分 + 具体扣分项 + 改进建议），触发 ReviewerRetryMiddleware；
  - 循环上限：MAX_REVIEW_RETRIES = 2，超限则带"当前最佳版本（已尽力）"返回用户；
  - 评分模型：建议用 qwen-max（评分质量优先），与主链路 qwen-plus 分离避免评分偏差污染主输出。
- **验收标准**：每份输出方案有 5 维评分明细；不通过案例 review_report.md 可追溯；循环不超过 2 次。

### FR-S12（v2 新增）LLM Gateway —— 限流/熔断/快慢隔离/降级【MVP（v1 P2 升级）】

- **描述**：模型调用前的统一网关，保护下游模型配额与本服务稳定性。
- **实现要点**：
  - **限流**：
    - 全局 `Semaphore`（如并发 50，对应 DashScope TPM 配额）；
    - 单用户 `Semaphore`（如并发 2）+ 滑动窗口 QPS（10/秒）；
    - 意图分类器独立配额（避免主对话被分类挤爆）。
  - **熔断**（Resilience4j 或自实现）：
    - 30 秒内失败率 > 50% → 熔断 10 秒；
    - 半开探测 → 正常后恢复。
  - **快慢隔离**：
    - 实时查询（天气/车票）走快车道（超时 5s）；
    - 行程规划/Reviewer 评分走慢车道（超时 60s），避免慢调用阻塞快调用；
    - 不同 Agent 池隔离线程池。
  - **降级**：
    - 主模型 `qwen-plus` 限流/超时 → 框架原生 `fallbackModel("qwen-turbo")` 自动切换
      （`ReActAgent.Builder.fallbackModel(...)` + `ExecutionConfig.builder().maxAttempts(3).timeout(...)` 重试退避，API 已核验）；
    - 仍然失败 → 返回"稍后重试"+ 写入 SSE error 事件，不白屏。
- **验收标准**：单用户刷爆不影响其他用户；主模型挂掉仍能响应（降级文案更简洁）；快慢调用互不阻塞。

### FR-S13（v2 新增）OpenTelemetry 全链路追踪 + 3A 评估【P1】

- **描述**：所有 Agent 调用接入 OTEL，自定义 span 标记意图/Worker/Reviewer/工具调用/Token 用量，落地到 Jaeger/Tempo；评估器异步打分入库。
- **实现要点**：
  - OTEL 集成：AgentScope 2.0 默认 OTEL 埋点（已内置），自定义 OtelTraceMiddleware 给关键节点打 span attribute（userId, sessionId, intent, worker, reviewer_score, total_tokens）；
  - 3A 评估：
    - **Availability**（可用率）：调用成功率 = 成功调用 / 总调用；
    - **Accuracy**（准确率）：Reviewer 评分 ≥ 80 的占比 + Bad Case 人工复审的准确率；
    - **Affordability**（性价比）：平均 Token 消耗 / 单次行程 + 平均响应时长。
  - 评估器：
    - **静态规则**：必含四维、时间衔接、名称匹配工具返回；
    - **LLM 评分**：qwen-max 评分器，对比方案与需求；
    - **人工复审**：管理员后台抽样标注。
- **验收标准**：Jaeger 可见每次对话完整链路；3A 看板有日/周/月趋势；Bad Case 自动聚类（按 Reviewer 扣分维度 + 错误类型）。

### FR-S14（v2 新增）Prompter 闭环 —— Prompt 自动调优【P2】

- **描述**：通过 Trace + Bad Case 自动迭代 Prompt，越用越好。
- **实现要点**：
  - PrompterRegistry 管理 Prompt 版本（System / Few-shot / Tool description 三类）；
  - 灰度：新 Prompt 5% 流量 → 评估通过 → 10% → 50% → 100%；
  - 自动改写：LLM（如 qwen-max）阅读 Bad Case + Trace，给出 Prompt 改动建议，人工 Review 后入库；
  - 评估：每次灰度对比 3A 指标，胜出则晋升。
- **验收标准**：每类 Prompt 至少有 v1/v2 两个版本可回滚；灰度期间 3A 指标有 A/B 对比看板。
